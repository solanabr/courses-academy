two root non-determinisms, not one bug

Why the two holes are holes

hole 1HashMap has no defined iteration order
// std randomizes the order per run, so
// "serialize entries in iteration order"
// yields different bytes each run.
use std::collections::HashMap;

let mut m = HashMap::new();
m.insert("a", 1);
m.insert("b", 2);
// for (k, v) in &m { ... }  <- NOT guaranteed
root causeThere is no canonical order to serialize. wincode and borsh each pick a resolution — and they pick differently ⇒ wire mismatch.
hole 2NaN is many bit patterns, and NaN != NaN
// A float can hold thousands of distinct
// NaN payloads, and none of them compare
// equal — not even to themselves.
let x = f64::NAN;

assert!(x != x);   // true
// so: which NaN do we write on the wire,
// and do we accept one on read?
root causeThere is no single NaN to write and no obvious accept rule. wincode and borsh disagree on both halves ⇒ f32 / f64 NaN is out of scope.
Each hole is a place where Rust itself leaves a choice open — two encoders, two answers.
